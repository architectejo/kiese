## BUG-130 — Créneaux horaires des équipes A/B (`Node`, backend)

Rapport source : `docs/qa/rapports/dev-backend-2026-11-09-bug129-creneaux-equipes.md`.

### Vérifications effectuées

1. **Relecture de code** :
   - `backend/core/models.py` : 4 champs `TimeField(null=True, blank=True)` confirmés sur `Node`,
     et `Node.active_team_at(when=None)` conforme à la description (intervalle semi-ouvert
     `[début, fin)`, priorité à A en cas de chevauchement, hypothèse « pas de créneau traversant
     minuit » documentée).
   - `backend/core/serializers.py::NodeSerializer` : les 4 champs bien exposés en lecture/écriture.
   - `backend/core/views.py::NodeViewSet.get_permissions()` : confirmé que seule `IsDirection`
     garde `create`/`update`/`partial_update`/`destroy` (pas `IsHeadquarters`) — un COMPTABLE
     (HQ au sens `is_headquarters` mais pas DIRECTION) ne peut donc pas écrire ces champs, exactement
     comme réclamé dans la mission.

2. **Rejeu des tests automatisés** : `python manage.py test core.tests.test_bug130_team_schedule`
   → **14/14 OK** (confirmé indépendamment, pas seulement relu dans le rapport). `python manage.py
   makemigrations --check --dry-run` → `No changes detected`.

3. **Reproduction indépendante de `active_team_at()`** (script `manage.py shell` ad hoc, scénarios
   non repris mot pour mot des tests existants) avec créneaux A=06:00-13:00 / B=13:00-20:00 :
   - 09:00 → `'A'`
   - 13:00 → `'B'` (borne de début de B incluse, pas de A)
   - 05:59 → `None` (avant tout créneau)
   - 20:00 → `None` (borne de fin de B exclue)
   - 19:59 → `'B'`
   - `datetime` naïf 07:00 → `'A'` (accepté sans lever d'exception)
   - Scénario de chevauchement A=06:00-15:00 / B=10:00-20:00, heure 12:00 → `'A'` (priorité à A
     confirmée)
   Tous les résultats correspondent exactement à la spécification du rapport dev-backend.

4. **Vérification API de bout en bout** (serveurs de dev réels, `demo_direction_e2e` /
   `demo_comptable_e2e`, mots de passe déjà utilisables — aucune manipulation `set_unusable_password`
   nécessaire pour ces deux comptes) :
   - `POST /api/core/nodes/` sans créneaux (DIRECTION) → les 4 champs valent `null` dans la réponse
     (aucune valeur forcée).
   - `PATCH` des 4 créneaux (DIRECTION) → 200, valeurs bien persistées.
   - `PATCH` d'un seul champ à `null` → seul ce champ repasse à `null`, les 3 autres inchangés.
   - `PATCH` d'un des champs par `demo_comptable_e2e` (COMPTABLE) → **403** confirmé en conditions
     réelles, pas seulement en test unitaire.
   - Nœud de test supprimé après vérification (`DELETE`, confirmé par requête directe en base :
     `Node.objects.filter(code='ZZE2E').count() == 0` après coup).

### Conclusion
**Aucun écart** avec le rapport `dev-backend`. BUG-130 → **VÉRIFIÉ**.

## BUG-131 — Formulaire frontend des créneaux horaires (`Nodes.tsx`)

Rapport source : `docs/qa/rapports/dev-frontend-2026-11-09-bug131-creneaux-frontend.md`.

### Vérifications effectuées

- Relecture de `frontend/src/pages/dashboard/Nodes.tsx` et `frontend/src/api/services.ts` :
  présence confirmée des 4 `<input type="time">`, des fonctions `toTimeInputValue`/
  `fromTimeInputValue`, et du typage `BakeryNode` étendu.
- Vérification manuelle sur serveurs de dev réels (frontend :5173 / backend :8000 déjà en cours
  d'exécution au moment de la mission) avec `demo_direction_e2e` :
  1. Route réelle confirmée : **`/admin/nodes`** (pas `/dashboard/nodes` comme deviné initialement —
     vérifié dans `frontend/src/App.tsx`, aucune anomalie, juste une précision de routage).
  2. Création d'une succursale `ZZMAN` sans toucher aux créneaux → ré-ouverture : les 4 champs
     horaires bien présents et vides (cohérent avec `null` côté API, vérifié en parallèle par
     BUG-130).
  3. Renseignement des 4 créneaux (06:00/13:00/13:00/20:00), sauvegarde, ré-ouverture → les 4
     valeurs pré-remplies correctement.
  4. Un seul champ vidé puis sauvegardé → seul ce champ revient vide à la ré-ouverture, les 3
     autres inchangés.
  5. Testé aux largeurs **360 px (pos)**, **768 px (tablette)** et **1440 px (bureau)** — spec
     Playwright ad hoc temporaire (supprimée après usage, non committée) : grille des créneaux
     lisible, modale sans débordement, interactions fluides aux trois largeurs. Les 3 exécutions
     sont passées (`3 passed`).
  6. Succursale de test supprimée via le bouton de suppression de l'UI ; confirmé en base
     (`Node.objects.filter(code='ZZMAN').count() == 0`).

### Remarque non bloquante (déjà signalée par dev-frontend, reprise ici sans la considérer comme
anomalie)
La page ne filtre pas elle-même par rôle qui peut *voir* le formulaire — elle s'appuie sur le menu
(déjà masqué pour les non-HQ, couvert par `02-connexion-roles.spec.ts`) et sur la garde backend
`IsDirection` (vérifiée réelle ci-dessus pour BUG-130). C'est cohérent avec le reste de
l'application (pas une régression propre à ce ticket) : aucune action requise.

### Conclusion
**Aucun écart** avec le rapport `dev-frontend`. BUG-131 → **VÉRIFIÉ**.
