### BUG-122 (Q-002) — Report de dette entre deux périodes de commission

- Décision appliquée (recommandation du coordinateur validée par le
  client) : report cumulatif, jamais remis à zéro, même logique que
  BP_client (CLAUDE.md §5.2).
- Implémentation choisie (documentée comme demandé par la mission) :
  nouveau champ `ClientCommission.carried_debt_in`, **recalculé
  automatiquement** par `compute()` (pas une valeur stockée en entrée) : à
  chaque appel, recherche la commission la plus récente du même client sur
  le même nœud, strictement antérieure à la période courante (peu importe
  un trou de génération) ; si son `net_payable` était négatif, la valeur
  absolue devient une déduction supplémentaire du net à payer courant.
  Choisi plutôt qu'une paire `carried_debt_in`/`carried_debt_out` car le
  `net_payable` de chaque période joue déjà naturellement le rôle de
  « solde sortant » pour la période suivante — pas de duplication d'état à
  synchroniser.
- Hypothèse appliquée sans reposer la question (autorisation explicite du
  cadrage de la mission) : si le client n'a pas de commission à la période
  immédiatement suivante, le report s'applique simplement à la prochaine
  période où une commission est générée pour lui, quel que soit l'écart —
  même principe que BP_client (jamais remis à zéro).
- Point intentionnellement non traité (documenté comme hypothèse, pas une
  ambiguïté bloquante) : un ajustement manuel (`manuel_adjustment`,
  DIRECTION) reste une décision explicite qui prévaut et n'est pas
  recombiné avec le report — cohérent avec le fait que l'override existant
  écrasait déjà entièrement la formule normale avant ce correctif.
- Fichiers modifiés : `backend/commissions/models.py`,
  `backend/commissions/migrations/0004_bug122_carried_debt_in.py`,
  `backend/commissions/serializers.py`, `backend/commissions/views.py`
  (3 `update_fields` complétés).
- Test : `backend/commissions/tests/test_bug122_carried_debt.py` (2 tests,
  nouveaux, échouaient avant — aucun champ/mécanisme de report — passent
  après). Suite `commissions` complète (26 tests) : OK.
- Impact API : champ additif `carried_debt_in` (lecture seule) sur
  `ClientCommissionSerializer` — non cassant. **Ticket lié ouvert pour
  dev-frontend : BUG-124** (affichage du champ dans le listing de paie /
  la fiche commission).

### BUG-123 (Q-005) — Coût matière du Compte de Résultat sur la consommation réelle

- Décision du client : consommation réelle (mouvements `EXIT`), pas les
  achats du mois (`ENTRY`).
- Problème annexe découvert en creusant, bloquant pour une bascule
  correcte : les mouvements `EXIT` n'avaient jamais de prix
  (`production/views.py::_record_consumable_exits` ne renseigne jamais
  `unit_price`, défaut `0.00`) — basculer le calcul sur `EXIT` sans corriger
  ce point aurait fait chuter le coût matière à 0.
- Implémentation choisie : Coût Unitaire Moyen Pondéré (CUMP).
  - Nouveau champ `ConsumableStock.average_unit_cost`, recalculé à chaque
    `ENTRY` (moyenne pondérée par quantité).
  - Chaque `EXIT` **fige** `unit_price` sur le CUMP courant du stock au
    moment de la sortie (même principe que `InvoiceLine.save()` figeant
    `unit_price` depuis `BreadPrice` — toute valeur transmise par
    l'appelant pour une sortie est ignorée, cohérence garantie quel que
    soit le point d'entrée : API, fournée, ou tout futur appelant).
  - Migration de schéma (`0017_bug123_consumable_average_unit_cost.py`) +
    migration de données réversible (`0018_bug123_backfill_average_unit_cost.py`)
    qui rejoue l'historique des mouvements déjà en base pour que le CUMP
    soit cohérent rétroactivement dès l'application du correctif (réversible :
    la migration inverse remet `average_unit_cost` à 0, l'état initial,
    aucune perte réelle).
  - `finance/views.py::_income_statement_for_year` : `movement_type='ENTRY'`
    → `movement_type='EXIT'` pour `cost_flour`/`cost_yeast`/`cost_salt`/
    `cost_oil` — même formule, même agrégat en une requête (BUG-066),
    **toujours couvert par l'index existant `prod_consmove_type_crea_idx`
    (movement_type, created_at)** : vérifié explicitement, aucune régression
    de performance (BUG-064/066/070) introduite par le changement de valeur
    de filtre.
- Impact vérifié sur les autres états financiers : **aucun**.
  `_balance_sheet_for_year` et `_cashflow_for_year` ne dépendent ni de
  `ConsumableMovement` ni des coûts matière — rien d'autre à changer.
- Fichiers modifiés : `backend/production/models.py`,
  `backend/production/migrations/0017_bug123_consumable_average_unit_cost.py`,
  `backend/production/migrations/0018_bug123_backfill_average_unit_cost.py`,
  `backend/production/serializers.py`, `backend/finance/views.py`.
- Tests : `backend/production/tests/test_bug123_average_unit_cost.py` (4
  tests, nouveaux) + `backend/finance/tests/test_income_statement.py`
  (scénarios adaptés/ajoutés : `test_entry_purchases_alone_do_not_affect_cogs`
  nouveau — échouait avant, passait achat seul en coût ; `test_exit_cost_is_
  valued_at_weighted_average_unit_cost` remplace l'ancien test qui validait
  la méthode « achats » ; `test_net_result_formula_matches_...` adapté pour
  consommer réellement le stock plutôt que de s'arrêter à l'achat).
- Impact API : champ additif `average_unit_cost` (lecture seule) sur
  `ConsumableStockSerializer` ; valeurs (pas la forme) de `cost_flour`/
  `cost_yeast`/`cost_salt`/`cost_oil` changent de méthode de calcul. **Ticket
  lié ouvert pour dev-frontend : BUG-125** (affichage optionnel du CUMP dans
  l'écran Intrants).
